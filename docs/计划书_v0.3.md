# 1. 项目定义

## 1.1 一句话定义

> **5v5、有爆破目标的、Apex 式自由移动的第一人称射击游戏，面向自己与小圈子对玩。**

## 1.2 差异化主张

市面上的竞技射击分为两派：

| 流派 | 代表 | 移动 | 判定 |
|---|---|---|---|
| 战术派 | CS / 瓦 | 慢、僵硬、移动中打不准 | 精确 |
| 机动派 | Apex / 泰坦陨落 | 快、自由、立体 | 容错大、低 tick |

**本项目要占据的空白格：**

|  | 移动中打得准 | 移动中打不准 |
|---|---|---|
| **移动快** | Quake / AFPS | **← 本项目（新增）** ／ Apex |
| **移动慢** | CF / COD（腰射流） | CS / 瓦 |

> **核心主张：移动自由度按 Apex 设计，命中判定按 CS 设计。**

这个组合在商业上没人做，原因不是技术不可行，而是商业产品必须照顾 100ms 延迟的广域网玩家。**本项目规模小、区域近，恰好是优势。**


### v0.2 更正：「市场空白」论证作废

原稿下面这句话**论证不成立**，特此划掉并替换（项目本身不受影响）：

> ~~这个组合在商业上没人做，原因不是技术不可行，而是商业产品必须照顾 100ms 延迟的广域网玩家。~~

**原因**：The Finals 已经站在这一格里（本计划书 §8.3 候选 A 自己就写了「接近 The Finals」），Apex 本身也占半个格子。所以「没有这个组合」是错的。

**替换表述**（这才是真正的差异化）：

> **同一件事做得更硬：64 tick、无宽容判定、局域网零延迟。**

三点里没有一项是「别人想不到」，全部是「别人做不到」——因为商业产品必须照顾广域网玩家。**这个论证站得住，而且和 §1.4 第 5 条（作品集价值）一致。**


## 1.3 目标玩家与规模

| 项 | 目标 |
|---|---|
| 玩家 | 自己 + 3–9 个朋友 |
| 网络 | 局域网 / 同城（ping < 30ms） |
| 平台 | Windows 优先，Linux 次之 |
| 商业化 | 无。不考虑盈利、不考虑发行 |
| 上线 | 无期限，做到能玩为止 |

## 1.4 成功标准

按优先级排序，**做到第 3 条就算成功**：

1. ✅ 一个人能跑、能滑、能爬墙，手感对
2. ✅ 两个人局域网对枪，命中判定准
3. ✅ 一局爆破能打完，双方都觉得"想再来一局"
4. 🔸 有 2 张以上的图，能轮换
5. 🔸 能作为求职作品集展示（"把 Q3 级手感复刻到现代引擎"）

## 3.2 为什么模拟层必须无 Godot 依赖

这是**全项目最重要的架构决策**，高于引擎选型：

| 理由 | 说明 |
|---|---|
| 确定性测试 | 同输入序列跑两次比对世界哈希，不需要 GPU、不需要启动引擎 |
| 可替换性 | 万一 Godot 方案走不通，逻辑仍在，可换渲染器 |
| CI 友好 | headless 环境能跑回归测试 |
| 调试边界清晰 | 崩溃时能立刻判断"是模拟层还是表现层" |
| 性能可控 | 不受 Godot 帧时间波动影响 |

**落地要求**：
- 纯 C++17 静态库，零第三方依赖（除标准库）
- 与 Godot 的边界只有一个头文件 + 一组 `extern "C"` 函数
- 提供一个独立 `headless_sim` 可执行程序，能在终端跑 tick 循环

## 3.4 事件通道（v0.2 新增）

原架构只写了状态流 `[id, pos, yaw, anim]`，**驱动不了任何瞬发事件**——枪口火焰、抛壳、命中火花、脚步、换弹开始、滑铲起步的镜头下沉，这些都不是「每帧状态」，而是「这一 tick 发生了一件事」。

**没有事件通道只有两个坏选择**：表现层轮询状态变化（会漏帧、回滚时错乱），或让 GDScript 反向查询 sim（破坏单向数据流 + 拖性能）。

### 设计

```c
struct SimEvent {
    uint32_t tick;       // 回滚时靠它丢弃「预测出来但被服务器否决」的事件
    uint16_t type;       // EV_MUZZLE / EV_IMPACT / EV_FOOTSTEP / EV_RELOAD ...
    uint16_t entity_id;
    Vec3     a;          // 位置（或起点）
    Vec3     b;          // 终点 / 法线
    int32_t  param;      // 材质 ID、伤害、武器 ID
};
```

| 规则 | 说明 |
|---|---|
| 环形缓冲 | 1024 条，模拟层写、表现层每帧消费并清空 |
| **必须带 tick** | 否则回滚重放时无法区分「已确认」与「被否决」的事件 |
| 事件不回滚 | 已发到表现层的事件不做撤销，靠 tick 号做「过期忽略」 |
| 事件不承载权威数据 | 伤害数字一律走快照，不走事件 |

**这是跨边界的两条通道之一，和状态流同等重要。**

## 3.5 实体与状态容器（v0.2 新增）

这个决定同时约束三件事：delta 快照的字段布局、回滚重放的可行性、回合重置的正确性。**等写到 M5 才定就晚了。**

| 项 | 规定 |
|---|---|
| 存储 | **稠密数组**（`std::vector<Entity>`）+ 空闲链表 |
| ID | `uint32`：低 24 位索引 + 高 8 位世代号 |
| 序列化顺序 | **按 ID 升序**（确定性） |
| 容器禁令 | sim 内**禁止**任何按指针哈希的容器（`unordered_map<Entity*>`） |
| 回合重置 | 遍历稠密数组逐个 reset，**不析构重建**（避免悬垂与分配抖动） |
| 快照字段 | 只序列化「变化可能」的字段，静态属性走 configstring 式一次性下发 |

**理由**：稠密数组保证遍历顺序确定；世代号防止「旧 ID 指向新实体」；升序序列化让 delta 比对成为纯线性差分。

## 5.4 与 Apex 的差异（需要自己调）

| 维度 | Apex | Red Eclipse 2 | 本项目取向 |
|---|---|---|---|
| 滑铲 | 动量保持 + 下坡加速，可长滑 | 落地瞬间触发，消耗 1 次 | 取中间：允许长滑但耗资源 |

## 5.5 确定性实现要求（最高风险项）

Apex 式移动与确定性物理**天然冲突**：Q3 的 pmove 确定性好，是因为它足够简单（盒体 vs 平面、固定顺序、无迭代求解）。滑铲/爬墙会引入：

- 多方向表面探测（法线阈值判定）
- 状态切换的边界条件（贴墙 → 墙跑 → 脱离）
- 吸附/攀爬的判定窗口

**每一处都可能引入非确定性**。控制手段（**强制规范**）：

| 规则 | 说明 |
|---|---|
| 碰撞查询固定顺序 | 不做空间分割的并行遍历，或保证归约顺序一致 |
| 固定步长 | 物理子步长固定，不随 dt 变化 |
| 禁止迭代求解器 | 不使用任何物理引擎的 solver |
| 状态切换用整数 tick 计数 | 不用时间累积（`float` 累加会漂移） |
| 禁用浮点不确定操作 | 不用 `fast-math`，不依赖 x87 |
| 每 tick 世界哈希 | 逐 tick 记录，任何偏差立刻暴露 |

## 5.9 穿墙与分步扫掠（v0.3 新增）

### 问题

pmove 每 tick 只做一次 trace，速度一高就会「跨过」薄墙：

| 速度 | 每 tick 位移（64 tick） | 对比 |
|---|---|---|
| 8.13 m/s（跑） | 0.127 m | 安全 |
| 15.24 m/s（滑铲） | 0.238 m | 危险 |
| 20 m/s（滑铲 + 下坡） | **0.313 m** | **超过常见隔墙厚度** |

玩家盒宽 0.81 m 不会穿人，但 **0.1–0.2 m 的薄墙会被直接跨过**。表现是「滑铲时偶尔穿进建筑」，而且极难复现。

### 解法：分步扫掠

Q3 的 `PM_SlideMove` 就是这个思路——把一次移动拆成 N 步，每步位移小于最薄墙：

```c
float dist = length(velocity) * dt;
int steps = (int)ceilf(dist / MIN_WALL_THICKNESS);
if (steps > MAX_SLIDE_STEPS) steps = MAX_SLIDE_STEPS;  // 防病态值

float step_dist = dist / steps;
Vec3 step_vec = normalize(velocity) * step_dist;

for (int i = 0; i < steps; i++) {
    trace_t tr = trace_box(pos, pos + step_vec, player_mins, player_maxs);
    if (tr.fraction == 1.0f) { pos += step_vec; continue; }
    pos = tr.endpos;
    // 命中：把剩余速度投影到接触面切向，继续
    velocity = clip_velocity(velocity, tr.normal, 1.0f);
    step_vec = normalize(velocity) * step_dist;
    if (++bumps >= 4) break;   // Q3 的 4 次碰撞上限
}
```

### 两个必须同时定的数

| 参数 | 建议值 | 说明 |
|---|---|---|
| `MIN_WALL_THICKNESS` | **0.15 m** | 地图最小墙厚，**写进地图制作规范** |
| `MAX_SLIDE_STEPS` | 4 | 与 Q3 的 `MAX_CLIP_PLANES` 对齐 |
| `bumps` 上限 | 4 | 防止凹角里反复滑动 |

> **这两个数要放在同一份配置里**：如果地图允许 0.05 m 的墙，但 pmove 按 0.15 m 算步数，穿墙依旧会发生。

### 验收判据

以 20 m/s 正面冲 0.1 m 薄墙，连续 100 次，**0 次穿透**。

## 5.10 武器移速系数（v0.3 新增，修正 §5.6）

### 来源

TacZ（继 COD）的 `GunData` 里有 `moveSpeed` 与 `weight` 两个字段，意味着：**不同武器持枪时，玩家移速不同。**

这直接推翻了 §5.6 的假设：

> ~~`max_speed = 8.13` 作为全局常量~~
> **实际移速 = `base_speed` × `weapon.speed_coefficient`**

### 数值参照

| 武器类型 | 系数 | 说明 |
|---|---|---|
| 冲锋枪 / 手枪 | 1.00 – 1.05 | 最灵活 |
| 步枪 | 0.92 | 基准 |
| 霰弹枪 | 0.90 | — |
| 狙击枪 | 0.80 | 明显变慢 |
| 机枪 | 0.75 | 最慢 |

### 影响面（这才是为什么必须现在定）

| 受影响的量 | 怎么变 |
|---|---|
| 加速度 | 目标速度变了，`accel` 的实际效果跟着变 |
| 滑铲初速 | 滑铲按当前速度加成，系数会传导 |
| 墙跑阈值 | `min_approach_speed` 要按系数缩放，否则重枪永远跑不上墙 |
| 冲刺速度 | 同理 |
| **受伤减速**（§6.10） | 三层系数叠加：武器 × 受伤 × 状态 |

### 架构建议

```c
float effective_max_speed(const Player& p) {
    return BASE_SPEED
         * p.weapon.speed_coefficient   // 0.75 – 1.05
         * p.status.slow_factor         // 受伤减速，1.0 / 0.85
         * p.move_state.speed_scale;    // 蹲/走/冲刺
}
```

**所有移动常量都以它为准**，不要在任何地方直接写 `8.13`。

### 一句提醒

COD 手感有一大块来自这里：**重枪走得慢，轻枪能绕后**。这是「移动 × 武器」的耦合，不是两个独立系统。

# 6. 武器与枪感

## 6.1 枪感的构成

> **枪感 ≈ 30% 数值矩阵 + 20% 后坐力表 + 50% 反馈（音效/动画/命中提示）**

| 组成 | 内容 | 是否可抄 |
|---|---|---|
| 数值矩阵 | 各移动状态下的扩散 | ✅ Red Eclipse 2 |
| 后坐力 | 每发固定偏移序列 | ✅ 结构可抄，数值自己要调 |
| 首发精度 | 第一发的扩散 | ✅ |
| 恢复曲线 | 停火后回正速度 | ✅ |
| 视角抖动 | view punch | ✅ |
| 音效 | 射击/命中/换弹/脚步 | ⚠️ 只能用免费素材 |
| 动画 | ADS/换弹/检视 | ⚠️ 需自制或 Mixamo |

### v0.2 补充：伤害与穿透字段（C7）

原 `WeaponDef` 只有 `damage / rpm / range`，**推不出 §6.4 的 TTK**——TTK 是派生值，输入是 `伤害 × 命中率 × 部位倍率 ÷ (HP + 护甲)`，四个里三个没定义。

```cpp
// 追加字段
float damage_near;            // 近距离伤害
float damage_far;             // 远距离伤害
float falloff_start;          // 衰减起点（米）
float falloff_end;            // 衰减终点（米）
int   penetration_count;      // 可穿透层数（0 = 不能穿墙）
float penetration_damage_scale; // 每穿一层伤害乘数（如 0.7）
float headshot_mult;          // 头部倍率（如 4.0）
```

**为什么穿透值得做**：地图是 brush 构成的，wallbang 是 Q3/CS 系最便宜、最有辨识度的机制之一，而且**能直接缓解「移动快打不准」带来的挫败**——隔着薄墙补一枪是很爽的。

**v0.1 范围**：只实现前四项 + 部位倍率；穿透放 v0.2。

## 6.3 后坐力：查表，不是公式

> **CS 的 AK 前 10 发是一条上升竖线，然后左右摆——那不是模拟出来的,是写死的。**

## 6.4 TTK 取值

| 游戏 | 有效 TTK | 前提 |
|---|---|---|
| CS | 0.1–0.4s | 站定精度高、判定准 |
| Apex | 1.5–2s | 移动快、有护甲 |
| **本项目** | **0.6–1.2s** | 移动快 → 命中率低 → 需比 CS 长 |

**理由**：移动越快，交火命中率越低。若沿用 CS 的 0.3s，会变成"谁先看到谁"的运气游戏，移动技术的价值反而被抹掉。


### v0.2 补充：TTK 的因果（不是拍脑袋）

评审指出原稿只说「取中间」，没给推导。正确的因果链是：

> **长 TTK 的真正作用，是给被击中的人留出用移动脱身的时间。**

这才是「高速移动」与「长 TTK」必须绑定的原因：

| 若 TTK 太短 | 若 TTK 太长 |
|---|---|
| 高速移动没机会脱身 → 移动退化成了「赶路」 | 交火拖沓 → 双方都能跑掉 → 谁也不先进攻 |

**取值流程**：

```
1. 定 HP（如 100）
2. 定单发伤害与射速 → 得到理论 TTK
3. 用命中率（高速移动下约 25–35%）折算 → 得到有效 TTK
4. 目标有效 TTK 落在 0.6–1.2s
5. 反推需要的 HP / 伤害 / 护甲
```

**验收**：用 bot 或真人对打 20 局，统计「从第一次命中到击杀」的中位数，落在区间内即可。


> **v0.3 提示**：TTK 与「追击终结机制」强耦合，见 §6.10。**只调 TTK 不解决追逃问题。**


## 6.5 命中判定：hitscan 还是弹道

| 方案 | 优点 | 缺点 |
|---|---|---|
| **hitscan**（推荐主武器） | 判定精确、延迟补偿简单 | 缺乏预判深度 |
| 弹道 + 下坠（Apex 式） | 有预判深度 | 网络同步复杂、精度下降 |

**结论**：主武器 hitscan，狙击/投掷物用高速弹道（400–600 m/s）。


### v0.2 补充：散布必须带距离维度（C5）

原 §6.2 的扩散表只有「移动状态」一维，意味着**惩罚对所有距离一视同仁**。而 parkour 只对近距离有意义（远距离你反正要停下）。结果是「移动的价值」和「能开枪的距离」刚好不重叠 → **高速缠斗变成双方泼水，谁也不想先进攻**。

**解法**（参数少、可控）：

```
spread = base_spread[移动状态] × distance_factor(距离)
```

| 距离档 | `distance_factor` | 效果 |
|---|---|---|
| 近（< 8 m） | 0.5 | 跑打可用 |
| 中（8–25 m） | 1.0 | 需减速 |
| 远（> 25 m） | 2.5 | 必须站定 |

### v0.2 补充：弹道必须线段扫掠（B2）

§6.5 原写「狙击/投掷物用高速弹道（400–600 m/s）」，**会穿人**：

```
500 m/s ÷ 64 tick = 7.8 m / tick
玩家碰撞盒宽 ≈ 0.8 m
→ 弹丸一 tick 跨过整个玩家
```

表现是「狙击枪时灵时不灵」，而且难复现。

**规定**：弹道一律用「**线段扫掠 vs 胶囊**」，与 hitscan 共用同一套 trace，只是起点终点不同。**这条写进 M6 验收标准。**

## 6.7 ADS 灵敏度缩放（极易被忽略）

开镜后 FOV 变小，鼠标灵敏度**必须按比例缩放**，否则瞄准会"飘"——这是玩家最能感觉到、但开发者最容易漏的一项。

```
sens_ads = sens_hip × tan(fov_hip / 2) ÷ tan(fov_ads / 2)
```

| 项 | 说明 |
|---|---|
| `fov_hip` | 腰射 FOV（如 90°） |
| `fov_ads` | 开镜 FOV（如 55°，或按倍率算） |
| 实现 | 每把武器独立配置 `ads_fov_scale`，切换时平滑插值 |

**验收标准**：开镜后横向划过整个屏幕，准星移动的"手感距离"应与腰射一致。

## 6.8 部位判定（v0.2 新增，C1）

> **原稿错误**：§2.2 否决骨骼 hitbox（正确），但 §12.1 用**单胶囊**做判定。一个胶囊意味着**打哪都一样**——那么「判定按 CS」在玩家侧没有任何可感知的表达。CS 的精确感，玩家是通过「一枪头」学到的。

### 设计：按高度分三段（不碰骨骼）

```c
float hit_multiplier(float hit_y, float feet_y, float height) {
    float r = (hit_y - feet_y) / height;   // 0 = 脚，1 = 头
    if (r > 0.82f) return 4.0f;            // 头
    if (r > 0.45f) return 1.0f;            // 胸
    return 0.7f;                            // 腿
}
```

| 段 | 高度范围（1.42 m 站立） | 倍率 |
|---|---|---|
| 头 | 1.16 – 1.42 m | ×4.0 |
| 胸 | 0.64 – 1.16 m | ×1.0 |
| 腿 | 0.00 – 0.64 m | ×0.7 |

**优点**：零骨骼、零动画依赖、完全确定性、10 行代码。**这是最便宜、收益最大的一处改动。**

**注意**：蹲下时 `height` 变化，分段自动跟随，不需要额外处理。

## 6.10 追击终结机制（v0.3 新增）

### 问题：移动快 + 长 TTK = 追逃

高速移动 + 1 秒 TTK ⇒ 打不死人 ⇒ 双方都能跑 ⇒ 战斗退化成追逃，**「谁也不先进攻」**。

| 游戏 | 怎么终结追逃 |
|---|---|
| CS | 一枪爆头（TTK 0.1s，跑不掉） |
| Apex | 技能位移封锁 + 护甲破碎 |
| 瓦 | 技能 + 高精度点射 |

**本项目两个都没有**，必须补。

### 三个候选

| 方案 | 成本 | 副作用 |
|---|---|---|
| **受伤减速**（COD 做法） | 低 | 会让「高速移动」的爽感打折 |
| **爆头即终结**（`headshot_mult` 提到 5–6） | 低 | 强化「精准」主张，但会催生「只瞄头」 |
| **追击时精度上升**（移动惩罚反向） | 中 | 反直觉，但鼓励「追上去打」 |

### 选定组合

| 机制 | 数值 | 理由 |
|---|---|---|
| 受伤减速 | **−15% 移速，持续 1.5 s**（可叠加刷新，不叠加幅度） | 止住「逃」 |
| 爆头倍率 | **×5**（原 ×4） | 奖励「准」，且与「判定按 CS」一致 |

> 两者互补：**减速让逃的人变慢，爆头让追的人有回报。**

### 验收

用 bot 对打 20 局，统计「交火开始到任一方死亡」的中位数，**应显著低于纯 TTK 理论值**（说明确实有人被终结，而不是双方都跑掉）。

# 7. 网络


## 7.0 时间基准（v0.2 新增）

> **原稿缺口**：直接从「不可靠 UDP + delta 快照」跳到「客户端预测」，中间没有服务器时间估计。**这是 Q3 `net_chan` 里最不显眼、但删掉就整个跑不起来的一层。**

客户端要预测，就必须知道「我现在模拟的是服务器的哪一 tick」。

| 项 | 做法 |
|---|---|
| `serverTime` 估计 | 快照携带服务器 tick 戳；本地 `serverTime ≈ 快照戳 + RTT/2` |
| `cmd.tick` | 本地估算的服务器 tick，允许前瞻 1–2 tick |
| 时钟漂移 | 用滑动平均平滑修正，**禁止瞬移**（跳变会导致画面抖动） |
| 时钟跳变 | 房主切窗口/卡顿后，服务器 tick 会落后于客户端；策略 = 客户端减速追赶，最多丢 2 个 cmd |
| tick 宽度 | `uint32`（64Hz 下 2.1 年回绕，够用；`uint16` 只有 17 分钟） |
| 时间来源 | **`std::chrono::steady_clock`**，不用 `system_clock`（会被系统校时打断） |

### 刚性要求

- 所有时间差计算用 `checked_sub` 或先判大小；`steady_clock` 原点是开机时刻，**开机不足 N 秒时减大数会下溢**（steel-front 的真实事故：上线首小时才炸）。
- 服务器 tick 单调递增，**不因暂停而回退**。

> **这一节应在 M0 和 tick 抖动一起验，不要等 M5。**

---

## 7.1 同步模型

| 层 | 方案 |
|---|---|
| 传输 | 不可靠 UDP + 序列号 |
| 快照 | delta 压缩（只传变化的字段） |
| 客户端 | 本地立即预测移动，服务器校正后平滑回正 |
| 服务器 | 权威：伤害、命中、胜负 |
| 插值 | 其他玩家在 2 个 tick 快照间插值 |
| 延迟补偿 | **⏸ 局域网阶段先不做** |

> **明确否决**：~~GameNetworkingSockets 的可靠有序通道~~ —— 快照必须是不可靠的，可靠流会 head-of-line blocking。


### v0.2 补充一：delta 的 baseline（B1）

「只传变化的字段」必须说明相对**哪一份**做 delta。

| 规则 | 说明 |
|---|---|
| baseline | 客户端**最近一次 ack** 的快照序号 |
| 连续丢包 | 丢失超过 N（建议 3）个快照 → **强制全量** |
| 若继续对过期 baseline 做 delta | 客户端解不出来 → 人物闪烁、道具消失、包体暴涨 |

Q3 用 `netchan` 的可靠通道传 configstring 并维护 `lastAcked`，丢包时自动退化全量。**这套必须抄。**

### v0.2 补充二：开火的权威边界（A4）

原 §7.1 写「服务器权威：伤害、命中、胜负」，同时又写「客户端预测移动」，**但开火没有单独说明**。两个具体后果：

1. **幽灵命中**：客户端预测「打中了」并弹 hitmarker，服务器判定没中 → 血条回滚 / 伤害数字消失。这是 FPS 最伤口碑的一类 bug。
2. **后坐力漂移**：`RecoilPattern` 的索引是「连续第几发」，属**客户端状态**。一发被判无效、或校正改变开火 tick，索引就错位，之后每一发都偏。

**三条规则（写死）**：

| # | 规则 |
|---|---|
| 1 | 客户端**只预测**：枪口位移、后坐力视角、音效、抛壳。**不预测伤害与 hitmarker**；hitmarker 一律等服务器事件 |
| 2 | 后坐力由服务器计算并随快照下发 `punch`；客户端保存 `old_punch` 做增量 |
| 3 | 每一发带 `(tick, shot_index)` 唯一标识，用于服务器回执对齐 |

> 局域网 <30ms 时，hitmarker 的 RTT 延迟感知不到，**代价很小**。

## 7.3 延迟补偿（v0.2 改为：必须做）

> **原稿结论被推翻**。原文写：「局域网 ping < 20ms，误差小于一个 hitbox 半径，所以先不做延迟补偿。」
> **这个推论不成立**：插值延迟不是 ping，是**固定的**。

### 算术

2 tick 插值 = 31.25 ms，这段时间目标一直在动：

| 目标速度 | 31 ms 内位移 | vs 盒半宽（16 unit ≈ 0.41 m） |
|---|---|---|
| 320 u/s（跑） | 10.0 unit | 安全 |
| 450 u/s（冲刺） | 14.1 unit | 临界 |
| 600 u/s（滑铲/墙跑） | 18.75 unit | **超出** |

### 为什么这条不能跳过

这不是「体验略糙」，而是**移动越快的人越难被打中，且原因与枪法无关**。核心主张是「打中靠本事」，而系统在高速段白送了 18 单位的不可归因误差——玩家每次 miss 都无法判断是自己的问题还是网络的问题。

**判定越严格，这个误差越显眼**（CS 式宽容 hitbox 会吃掉它，本项目不会）。

### 解法

| 措施 | 成本 | 效果 |
|---|---|---|
| **插值缓冲从 2 tick 降到 1 tick（15.6 ms）** | 极低 | 600 u/s 位移降到 9.4 unit，进入安全区。代价：丢包时会抖，局域网可接受 |
| **第一天建 hitbox 历史环形缓冲**（64 tick × 1 秒） | 约 50 行 | 服务器回溯的前提 |
| **回溯命中判定** | M6 | 用历史 hitbox 而非当前 hitbox |

> **关键**：环形缓冲现在写约 50 行；M5 之后补等于重做同步层。

### 仍未做的部分

- 完整 lag compensation 的「客户端时钟对齐」细节（需要 §7.0 的时间基准先落地）
- 高延迟（>100ms）下的补偿策略（本项目不做）

## 7.6 预测与回滚策略（v0.2 新增，A5）

> **这是全项目最难的一处，而且改起来等于重写 pmove。**

Q3 的 pmove 可以被覆盖而无感，因为它状态小、且**纠正不改变玩家的未来选项**。加了 impulse 之后不一样了：一次纠正可能退还或吞掉一次冲刺，玩家会立刻感觉到「我刚才明明还能再翻一次」。

### 三个选项

| 方案 | 正确性 | 成本 | 体验 |
|---|---|---|---|
| ① 完整回滚（保存 N tick 状态，收到快照后重放） | 最高 | 最高 | 最好 |
| ② 状态权威 + 位置预测（能力是否触发由服务器定） | 中 | 低 | 按键要吃半个 RTT |
| ③ 全客户端权威 + 事后校验 | 低 | 最低 | 偶发不一致 |
| ~~② 状态权威~~ | — | — | **否决**：「按了爬墙没反应」比「位置回弹」更突兀 |

### 选定：① 的简化版——**只回滚本地玩家的移动状态**

不回滚世界，只回滚这一个玩家的：

```c
struct MoveSnapshot {
    uint32_t tick;
    Vec3     pos;
    Vec3     vel;
    uint8_t  impulse_count;
    uint8_t  parkour_state;
    uint16_t timers[4];   // slide/wallrun/climb/dash 的剩余 tick
};
// 约 50 字节；1 秒 = 64 tick = 3.2 KB
```

**成本远低于「完整回滚」的直觉估算**，因为移动状态本来就极小。

### 流程

```
1. 本地每 tick 存一份快照，同时执行输入
2. 服务器快照到达 → 找到对应的 tick
3. 若位置/状态一致 → 丢弃历史
4. 若不一致 → 从该 tick 重放后续输入（最多 1 秒）
5. 重放期间冻结「新输入」，避免二次分叉
```

## 7.8 确定性随机（v0.3 新增）

### 问题

后坐力的随机分量、霰弹散射、弹孔偏移、粒子，都需要**客户端与服务端产生同一个随机数**。

| 做法 | 后果 |
|---|---|
| ~~共享一个 RNG 状态~~ | 回滚/重放时状态对不上，**每次重放结果都不同**，demo 完全失效 |

### 解法：无状态计数式随机（counter-based RNG）

```c
// 不保存任何状态，每次从「坐标」推导
uint32_t rng_at(uint32_t tick, uint16_t entity_id, uint16_t index, uint32_t salt) {
    uint32_t x = tick * 0x9E3779B9u
               ^ (uint32_t)entity_id * 0x85EBCA6Bu
               ^ (uint32_t)index * 0xC2B2AE35u
               ^ salt * 0x27D4EB2Fu;
    x ^= x >> 16; x *= 0x7FEB352Du;
    x ^= x >> 15; x *= 0x846CA68Bu;
    x ^= x >> 16;
    return x;                      // 或映射到 [0,1)
}
```

| 特性 | 好处 |
|---|---|
| 无状态 | 回滚/重放/并行天然安全 |
| 可寻址 | 任意 tick 的任意事件都能独立复算 |
| 可验证 | 两机同 tick 同 index 必得同值 |

### 使用清单

| 场景 | 种子组成 |
|---|---|
| 后坐力随机分量 | `(tick, player_id, shot_index)` |
| 霰弹散射 | `(tick, player_id, shot_index, pellet_index)` |
| 弹孔偏移 | `(tick, entity_id, impact_index)` |
| 粒子 | `(tick, event_index)` |

> **禁令**：sim 内**禁止**使用 `rand()` / `std::mt19937` / 任何带状态的 RNG。

## 7.9 输入队列与性能预算（v0.3 新增）

### 输入队列

客户端发 cmd 的节奏与服务器 tick 不完全同步（网络抖动、客户端帧率波动）。

| 缓冲深度 | 后果 |
|---|---|
| 太小 | 丢输入 → **吞键** |
| 太大 | 增加延迟 → 手感**粘** |

| 参数 | 建议值 |
|---|---|
| 服务器输入队列 | **2 tick（31 ms）** |
| 溢出阈值 | > 4 tick 丢弃最旧 + 记录日志（这是病态网络） |
| 客户端发送频率 | 每 tick 发 1 个，附带最近 3 个（防丢包） |

### 性能预算（64 tick = 15.625 ms）

| 项 | 预算 |
|---|---|
| **模拟（pmove + 碰撞 + 武器 + AI）** | **< 4 ms** |
| 网络序列化 | < 1 ms |
| 表现层（渲染） | < 8 ms |
| 余量 | ≥ 2 ms |

**这是硬指标，进 CI**：超过 4 ms 会出现 tick 累积，表现为「人物瞬移」。

> 测量方式：Tracy 看单 tick 的 sim 区间；CI 里跑 1000 tick 取 p99。

### v0.2 补充：拆包缺三个参数

评审指出：「单手、可移动」已定，但仍缺三项，必须在画图前定。

| 参数 | 选项 | 影响 |
|---|---|---|
| **能否开枪** | 能 / 不能 | 能 → 拆包不是「活靶子」，但会变成「边打边拆」 |
| **几秒** | 3 / 5 / 8 | 与移动速度直接相关：越快，拆包时间应越长 |
| **打断后进度** | 归零 / 保留一半 / 保留 | 保留 → 更鼓励反复骚扰 |

**建议初值**：能开枪（副武器）/ 5 秒 / 归零。理由是高速移动下，拆包者必须能自保，否则没人愿意拆。

### v0.2 补充：C3 —— impulse 上限必须从回防时间反推

> **RE2 的 6 次是从竞技场死斗搬来的**，那里没有目标点、移动免费。本项目是**有回防时间约束的目标点攻防**：6 次连续 parkour 意味着防守方可以从任意位置几秒内到达任意点，**地图设计里的「旋转时间」这个核心约束会直接失效**。你会发现自己画的每张图都「守方太快」，然后开始堆走廊和门，把立体移动的乐趣又堵回去。

**算法**：

```
1. 定「A 点纯跑 → B 点」的秒数（例：8s）
2. 定「全程 parkour 最快」的秒数（例：5s）
3. 差值 3s = 这张图允许的机动优势
4. 调 impulse 上限，使最大收益 ≈ 3s（例：3–4 次）
```

**顺序要求：先画图，再定数值。** 反过来会画出一堆「守方永远太快」的图。

## 8.5 垂直预算（v0.3 新增）

### 问题

Apex 式移动会让地图**自然长出很多层**，但爆破需要**可读性**：玩家必须知道「敌人在哪一层」。

CS 的图几乎全是单层 + 少量高台，这是刻意的。

### 硬约束

| 项 | 规定 |
|---|---|
| 每张图最大层数 | **2.5 层**（地面 + 一层 + 少量高点） |
| 楼层视觉区分 | **必须**用不同材质/色调，不能只靠高度 |
| 层间通道 | 每两层之间至少 2 条路径（避免单点封锁） |

### 为什么是 2.5

超过 3 层，玩家会开始「听到脚步但不知道在哪」——这是**立体射击游戏最常见的体验崩塌点**。

### 音频补充

层间如果只靠普通 3D 音频，**上下几乎不可辨**。两种解法见 §9.2。

## 10.3 测试（最关键的三件）

| 测试 | 实现 | 价值 |
|---|---|---|
| **确定性回归** | 同输入序列跑两次，逐 tick 比对世界哈希 | 50 行代码，netcode 的保命线 |
| **demo 录制/回放** | 记录输入 + 种子，可逐 tick 回放 | "打中了没判定"类 bug 的唯一排查手段 |
| **网络劣化** | Linux `tc netem` / Windows `clumsy`，模拟 80ms + 2% 丢包 | 不测这个，局域网练出的手感一到真实网络就废 |


### v0.2 修正：确定性哈希必须提前到 M1（D1）

原计划把它排在 M4（第 7 周），**这是全项目性价比最高的 50 行代码，却排在最晚**。

一旦非确定性在 M1–M3 之间混进来（而它一定会混进 parkour 的状态切换里），到 M4 你面对的是一片写了 7 周的代码，只能靠二分注释去找。**M1 就有「同输入跑两次、逐 tick 比哈希」，任何一天引入的漂移当天就会红。**

### v0.2 修正：确定性目标降级（不追求跨机 bit-exact）

| 场景 | 要求 |
|---|---|
| 同机双进程（listen server 房主） | **bit-exact**（同 libm、同指令集，免费） |
| 跨机（其他玩家 vs 主机） | 容差：1 秒内偏差 < 0.01 m |
| Linux 客户端 | 保留，但标注「可能有细微偏差」 |

> ~~跨机器 bit-exact~~ 是 lockstep RTS 的需求。本项目要的是「预测偏差足够小且可被平滑吸收」，这样可以省掉大量在 `-ffp-contract`、libm 差异上的时间。

### v0.2 修正：demo 与构建版本绑定（B3）

**原稿自相矛盾**：§10.3 说 demo 是「打中了没判定」类 bug 的**唯一**排查手段，§10.4 又要求「每天都应有可双击运行的版本」。回放要逐 tick 复现就要求**同一个二进制**，而每日构建意味着「昨天那个 bug 的 demo，今天回放不出来了」。

| 措施 | 说明 |
|---|---|
| demo 头写入 | `build_hash + sim_version + 协议版本` |
| 不匹配时 | 允许「尽力播放」，但**显式警告** |
| 发版前 | 留一份带符号的存档二进制 |


## 10.4 版本管理

| 项 | 要求 |

| **Git LFS** | 12GB 动画 + 地图源文件，第一次 push 就会炸 |

# 15. AI 协作开发规范（v0.2 新增，v0.3 扩充）

> **来源**：`Jerry-Hang/steel-front` 的 `AGENTS.md`（694 行 / 64 KB，从 **1334 次提交里的 283 个 `fix`** 中提炼）。
> **适配说明**：原项目是 Rust + Vulkan，本项目是 C++ + Godot，具体命令不同，**方法论完全通用**。

## 15.1 第一原则：把上下文当稀缺资源

AI 会话的入口文档会被**完整注入**，它是有硬上限的。

| 文件 | 放什么 | 体量纪律 |
|---|---|---|
| `AGENTS.md` | **只放仍然生效的约束**：铁律 / 未结案 / 教训 / 验收红线 | 目标 < 48 KB，**硬上限 64 KB** |
| `docs/PROGRESS.md` | 进度、日志、交接历史 | 不设上限 |
| `docs/pitfalls/` | 历史事故总集，按主题分档 | 按需 |

### 三条铁则

1. **被推翻的约束直接删掉**，不留「错误版 + 更正版」两段
2. **已结案的只留一行结论 + 判据**，细节进 PROGRESS
3. **进度一律写进 PROGRESS.md**，不写回 AGENTS.md

> 实测：steel-front 的 AGENTS.md 曾膨胀到 **200 KB，三分之二是重复段落与没删的旧结论**。超过 65536 B 会被**真截断**——2026-09-26 末条教训就被截掉了，注入进来的是残的。
>
> **加内容之前先问一句：「三个月后还成立吗？」**

## 15.2 铁律的形式：领域 + 日期 + 代价 + 判据

steel-front 的八条铁律（A 渲染路线 / B 渲染约定 / C 输入键位 / D 建模资产 / E 平台线程 / F 协作上下文 / G 凭据白名单 / H 导航寻路）都是同一个模板：

```
铁律 X — 领域（日期 立，代价 = 什么坏了）

- 规则（肯定句，可直接执行）
- 🔴 反例（怎么坏的，带实测数字）
- 判据 = 怎么验（命令或指标）
```

**要点**：

| 要写 | 不要写 |
|---|---|
| 为什么立这条（代价） | 背景故事 |
| 怎么坏的（具体现象 + 数字） | 「之前遇到过问题」 |
| 怎么验（可执行判据） | 「注意一下」 |

**本项目建议的铁律清单**（v0.3 开始逐条立）：

| 编号 | 领域 | 首条内容 |
|---|---|---|
| A | 单位制 | 全文禁 `u/s`/`unit`，只在 §5.6 换算表出现 |
| B | 确定性 | 禁止迭代求解器、禁止指针哈希容器、固定步长 |
| C | 边界 | 跨 GDExtension 只走状态流 + 事件通道两条 |
| D | 网络 | 快照走不可靠通道，禁可靠流 |
| E | 性能 | 每帧分配为 0，容器预分配 |
| F | 协作 | 见 15.5 |
| G | 凭据 | 密钥不进仓库，从环境变量读 |
| H | 内容 | 素材许可清单，进仓库前登记 |
| **I** | **手感数值** | **任何影响手感的数值必须可热重载**（改数值不重编、不重启） |

## 15.3 三层结构：铁律 / 未结案 / 教训

| 层 | 特征 | 维护规则 |
|---|---|---|
| **铁律** | 长期约束，少而硬 | 只在「付过代价」时新增 |
| **未结案** | 按「值不值得下一轮动手」排序 | **每条必须给 lead；没有 lead 的不要瞎猜** |
| **教训** | 编号沿用历史、**不复用** | 每条只留可执行判据，案例进 PROGRESS |

> steel-front 的教训清单是 **46 个编号 / 44 条内容**（23 并入 8、35 并入 43），编号沿用不复用——**这样引用「教训 27」永远不会指向错的东西**。

## 15.4 判据纪律（最容易失效的地方）

这一层是整套方法里最值钱的部分。**所有条目都来自真实事故。**

| # | 纪律 | 事故形态 |
|---|---|---|
| 1 | **恒真的断言等于没写** | `npcs.len() >= 0`；回归测试把错误结论固化下来 |
| 2 | **警惕结构性恒真** | 验证层关着时日志里没有 VUID，`vuid == 0` 永远成立 |
| 3 | **审计工具必须有第三种结局** | `0 = 扫过无命中 / 1 = 有命中 / 2 = 根本没扫成`。空日志不算通过 |
| 4 | **先确认工具测的是你以为的东西** | 一个会话为此栽了六次 |
| 5 | **用「必然能测出差异」的已知变化验一次工具** | 否则你不知道它是不是瞎的 |
| 6 | **先有结论，再写一个刚好能证明它的工具** | 一晚踩了四次 |
| 7 | **阈值越线先判是不是首帧窗口** | 别改测试、别调阈值 |
| 8 | **「没有豁口」≠「闭合」** | 围墙测试全绿，而四角是开口的 |
| 9 | **视觉改动的验收必须给两个数** | 两次运行场景一致；整幅 diff 不能当改善幅度 |
| 10 | **单次 A/B 说明不了任何事** | 必须正对照臂 + 同轮轮转 + 每臂 ≥5 对 + 先量 A/A 底噪 |
| 11 | **小于 A/A 噪声底的差不算数** | 1 对噪声 ±20% ⇒ 1~5% 的效应测不出 |
| 12 | **扫描类判据的自检要写「必须有一部分成功」** | 「没 panic」在接受率 0/3000 时什么都没证明 |
| 13 | **工具跑不起来本身就是缺陷** | 不能写成「已知限制」然后长期不开 |
| 14 | **别用「看着像什么」代替验证** | 先看日志再看图；截图是崩溃前的最后一帧 |

### 本项目的判据清单（建议）

| 判据 | 阈值 | 工具 |
|---|---|---|
| tick 间隔 p99 | < 16.5 ms | `tools/tick_probe` |
| input-to-photon | < 25 ms（中位数） | 240fps 慢动作拍 20 次 |
| 确定性 | 同输入两次逐 tick 哈希一致 | `headless_sim --hash` |
| 跨机偏差 | 1 秒内 < 0.01 m | 两机对比日志 |
| 零警告 | `-Wall -Werror` 通过 | CI |
| 帧分配 | 稳态下 0 次 | Tracy |
| 冒烟 | 不崩 + 能进图 + 能开一枪 | `run_smoke` |

## 15.5 变更纪律

| # | 规则 | 理由 |
|---|---|---|
| 1 | **并行分身：文件集两两不相交** | 同一文件被两个 agent 改必然互相覆盖 |
| 2 | **分身禁止 build 与 git** | 单一构建资源会被抢；git 索引会锁 |
| 3 | **大模块禁整文件重写，只许精确 edit** | 上万行的文件重写必然丢内容 |
| 4 | **开工前先把在飞改动 commit 成干净基线** | 否则回滚回不到「已知好」的状态 |
| 5 | **改共享代码必须双模式验证** | 例如第一人称 + 检视模式都要看 |
| 6 | **未结案条目会过期** | 动之前先 `grep` 确认引用的符号还在；**结案必须把条目本身改掉或删掉** |
| 7 | **dead code 必须回答「为什么没接线」** | 不许 `[[maybe_unused]]` 了事 |
| 8 | **新结论与旧约束冲突时，删掉旧的那条** | 两份并存等于没有 |
| 9 | **一个功能一个 commit，禁止 mega-commit** | 二分定位的前提 |

> **本项目特别注意**：同一文件的**多处修改严禁并行**。已验证的踩坑形态是 5 处并行编辑导致 2 处段落损坏 + 2 处注记丢失 + 1 行残片。**正确做法：单个脚本一次读、一次改、一次写回。**

## 15.6 安全纪律

| # | 规则 |
|---|---|
| 1 | **密钥一律不进仓库**，包括「先提交、回头再删」——历史 blob 清不掉，公网爬虫会收割 |
| 2 | 密钥只从**环境变量**或仓库外文件读，文档写占位符 `<YOUR_KEY>` |
| 3 | 提交侧设**默认拒绝**的白名单闸门，放行要改白名单（改动即留痕） |
| 4 | 脚本文件**行尾必须是 ASCII**（PowerShell 5.1 按 GBK 读无 BOM 文件，中文行尾会吃掉下一行） |

> steel-front 真实事故：`scripts/vision_ps.ps1` 硬编码 API key 并推送到公开远端，2026-08-21 发生。

## 15.9 每次新会话的开场协议

```
1. 读 docs/AGENTS.md（约束）
2. 读 docs/PROGRESS.md 最后一节（上次停在哪）
3. 跑一次 smoke（确认基线是绿的）
4. 只改一个文件集
5. 改完立刻 commit（一个功能一个 commit）
6. 更新 PROGRESS.md
```

> **第 3 步不能省**：如果基线本来就是红的，你会把别人的 bug 当成自己改坏的。

## 15.10 从 steel-front 直接可抄的十条

| # | 教训 | 通用化 |

| 1 | 先读文档再动手 | 「曾花大半天重新发现三天前写下的结论」 |
