## 0. 本文的由来与边界

起因是一次对 Minecraft 基岩版 SoulSteel 服务器「成都裸连英国几乎无感」的技术复盘。复盘结论是：那个体验由三部分组成——

| 组成 | 是否真实存在 | 对本项目价值 |
|---|---|---|
| WebRTC 式传输（NetherNet：TCP 信令 + UDP 媒体） | 真实 | 中（只借分层，不借栈） |
| 服务端权威 + 客户端预测 + 回退重放 | 真实，且是体感主因 | **极高** |
| Azure anycast 就近接入 + 骨干 | 能力真实，但无证据用于该服务器 | **接近零，且有负作用** |

**边界声明**：本文只讨论「网络与同步层」，不碰 pmove 数值、武器参数、地图格式。凡与 §5/§6/§8 冲突的地方，一律以 v0.3 为准，本文只提出待裁决项。

## 1. 价值排序（与商业产品相反）

商业 FPS 的网络设计有一条隐藏前提：**必须先让最差的那 5% 玩家能玩**。20Hz、宽容 hitbox、200ms 回溯窗口、0.5 秒的命中容差，全部是这个前提的产物。

本项目的目标玩家是 3–9 个朋友、局域网或同城（§1.3，ping < 30ms）。这个前提不存在，于是价值排序整个翻转：

| 优先级 | 能力 | 商业产品地位 | 本项目地位 |
|---|---|---|---|
| P0 | 确定性模拟（可重放、可哈希） | 加分项 | **生存前提**（R1/R19） |
| P0 | 预测 + 回滚（本地移动） | 标配 | 标配，且可做得更激进 |
| P1 | 控制面/数据面分离 | 标配 | 必做，否则 configstring 会堵快照 |
| P1 | 延迟补偿（回溯命中） | 标配 | **必做**（§7.3 已改判） |
| P2 | 打洞 / 中继 | 标配 | 需要，但只在跨网时 |
| P3 | anycast 接入、骨干优化 | 云厂商卖点 | **不做** |

**核心原则（写进 §2.1 决策表）**：

> **借架构，不借参数。** NetherNet 的所有阈值、缓冲深度、回溯窗口都是为 200ms 玩家放宽的；本项目只取它的分层方式，参数一律按 30ms 重算。

## 2. A1：控制面 / 数据面分离

### 2.1 为什么要做

§3.5 已定「静态属性走 configstring 式一次性下发」，§7.7 已定「加入/重连发 full_state」。这两类数据有两个特征：**大**（地图清单、材质表、武器配置可能几百 KB）和**必须完整**（缺一条就渲染错）。把它们塞进每 tick 的 UDP 快照通道，会造成三个后果：

1. 单个 configstring 包超过 MTU → 必须分片 → 丢一片就卡住整包；
2. 可靠重传与快照抢同一个发送队列 → 快照被推迟 → tick 抖动；
3. 加入/重连瞬间的突发流量打乱所有人的快照节奏。

NetherNet 的解法是把这两件事彻底分开：信令与握手走 TCP/HTTPS，游戏数据只走 UDP。这不是新技术，Q3 时代就有对应物（`netchan` 的 reliable 通道 + `svc_setconfigstring` 分块），但 NetherNet 把它做成了**协议级的两条独立连接**，避免互相影响。

### 2.2 落地设计

| 项 | 规定 |
|---|---|
| 信令传输 | **TCP**，HTTP/1.1 或裸长度前缀帧；localhost 阶段可同进程 |
| 信令端口 | `27015/tcp`（与游戏端口错开，便于防火墙规则分开写） |
| 游戏传输 | **UDP**，`27016/udp` |
| 中继传输 | **UDP**，`27017/udp`（v0.2 才启用） |
| 编码 | 二进制长度前缀帧（`uint16 len` + payload），不用 JSON——省得为一个 `player_name` 引 ICU |
| 大资产 | 走 HTTP GET + `Content-Hash`，客户端按 hash 落盘缓存；**不进内存协议** |
| 线程模型 | 信令在独立线程，产出的事件通过无锁队列投递给 sim 线程；sim 线程**禁止**发起阻塞 IO |

**信令消息表（v0.1 只需 6 条）**：

| 消息 | 方向 | 内容 | 可靠性 |
|---|---|---|---|
| `HELLO` | C→S | 协议版本、client_id、ticket（可空） | 必达 |
| `HELLO_ACK` | S→C | 接受/拒绝原因、服务器 tick、config hash | 必达 |
| `ASSET_MANIFEST` | S→C | 资产名 + hash + 大小列表 | 必达 |
| `ASSET_READY` | C→S | 本地已具备的 hash 集合 | 必达 |
| `MATCH_START` | S→C | 地图、规则、初始阵容、随机种子 | 必达 |
| `FULL_STATE` | S→C | 中途加入/重连的全量状态（§7.7） | 必达 |

**时序（冷启动）**：

```
C                         S
|-- HELLO --------------->|   协议版本不匹配 → 直接拒绝，别尝试兼容
|<-- HELLO_ACK -----------|   带 config hash
|<-- ASSET_MANIFEST ------|
|-- ASSET_READY --------->|   只报「我没有的」，全有则空集
|   (HTTP GET 缺的资产)    |   与 UDP 握手并行，不阻塞
|-- UDP 打洞/连通性检查 -->|   见 A3
|<== MATCH_START =========|
```

**判据**：
- 冷启动到可操作 < 3 秒（局域网，资产已缓存）；
- `configstring` 全部到齐前，**旧配置继续生效**，不允许「半套配置」上线（否则模型/材质缺失会以「隐形人」形式出现，且难以归因）。

### 2.3 与 Godot 的边界

GDScript 侧只消费 `SimEvent` 与状态流（§3.4），**不参与任何网络逻辑**。信令线程产出的「资产就绪」「房间状态」也必须转成事件入环形缓冲，不能让 UI 直接读网络状态——否则回滚时 UI 会闪。

## 3. A2：可靠流与不可靠流并存

### 3.1 决策重申

§2.2 已否决 GameNetworkingSockets，理由是可靠有序流的 head-of-line blocking 会拖累快照。**这个否决是对的，但否决的不是「可靠性」，而是「所有数据共享同一条有序可靠流」。**

NetherNet 用 SCTP 的多 DataChannel 解决了这一点：可靠流和不可靠流各自独立，互不阻塞。本项目不需要 SCTP（太重），但**必须自己实现「一条 socket、两个发送队列、两种语义」**。

### 3.2 最小可靠层规格

| 参数 | 建议值 | 依据 |
|---|---|---|
| 可靠序号空间 | 独立于快照序号（`rel_seq`） | 避免与 delta baseline 混淆 |
| 窗口 | 32 包 | 64Hz 下约 0.5 秒在途 |
| 单包有效载荷 | ≤ 1024 B（留 MTU 余量） | 见 B1 |
| ACK | 累积 ACK + 位图（32 位） | 抗连续丢包 |
| RTO 估计 | RFC 6298：`SRTT`、`RTTVAR`、`RTO = SRTT + max(1ms, 4×RTTVAR)` | 别用固定超时 |
| 初始 RTO | 250 ms（局域网），min 100 ms，max 1 s | 局域网首包快 |
| 重传上限 | 5 次 → 判定断线，转入重连流程 | 与 A5 联动 |
| 分块 | `configstring` 按 512 B 分块 + CRC32 | 整块校验失败就重传该块 |

**包结构（位级）**：

```
[0]      uint8   pkt_type      // 0=SNAPSHOT 1=RELIABLE 2=ACK 3=CONNECT 4=PING
[1]      uint8   flags         // bit0: fragmented, bit1: ack_bitmap_present
[2..3]   uint16  seq
[4..5]   uint16  ack
[6..9]   uint32  ack_bitmap
[10..]   payload
```

**为什么 ACK 要位图**：局域网内连续丢两个包的场景很少但存在（尤其是 Wi-Fi），纯累积 ACK 会触发不必要的整体重传，把 200 字节的配置重发成 2 KB。

### 3.3 双队列调度（与 B3 合并实现）

```
每 tick:
  1. 打包 SNAPSHOT（每客户端一份 delta）
  2. 全部塞进高优先队列
  3. 发送循环：先清空高优先队列
  4. 若当前 tick 还有 MTU 预算（每 tick 允许发 2 个包），从可靠队列取 1 个
  5. 可靠队列为空 → 不发空包（UDP 无 keepalive 需求，靠 PING 心跳）
```

**判据**：连续 10 秒内，SNAPSHOT 的发送延迟 p99 < 1 ms；`configstring` 下发期间，快照 tick 间隔不变（对比无下发的基线，偏差 < 0.5 ms）。

## 4. A3：打洞与中继（跨网时的最小实现）

### 4.1 现状与问题

§7.5 目前只有一句：「参考 Steel Front 的 `rdv`，极简文本式 UDP 房间名解析 + 打洞中继，端口 27015/27020。估算 2–3 天。」

这句话的问题不在工期，而在**没有失败路径**。真实的 3–9 人场景里，至少会有一个玩家处在对称 NAT 或运营商级 NAT（CGNAT）后面——此时打洞必失败，必须有中继兜底，否则那一局就开不起来。

### 4.2 候选与优先级

沿用 ICE 的模型，但砍掉 trickle（一次性收集完再交换，省 1–2 天）：

| 候选类型 | 来源 | 优先级 | 说明 |
|---|---|---|---|
| host | 本机网卡地址 | 126 | 局域网内直接命中，最优 |
| srflx | STUN 反射地址 | 100 | 普通 NAT 后的公网映射 |
| relay | 中继服务器分配 | 0 | 仅在前两类全失败时使用 |

优先级公式可直接抄 ICE：
`priority = (2^24)×type_pref + (2^8)×local_pref + (256 − component_id)`

### 4.3 连通性检查与选路

| 项 | 值 |
|---|---|
| 检查包 | 简化 STUN Binding Request（或自定义 `PING` + 随机 nonce） |
| 间隔 | 50 ms |
| 单次超时 | 250 ms |
| 重试 | 5 次 → 该候选判死 |
| 选路 | 所有「通」的候选中取 **RTT 最小**；若最小 RTT 的丢包率 > 2%，改选次优 |
| 切换策略 | **仅在开局前选择一次**，局中不切换（见 §12 anycast 的反面教材） |

**判据**：
- 同一局域网：host 候选命中率 100%，选路耗时 < 100 ms；
- 一方对称 NAT：能在 3 秒内降级到 relay，且不阻塞开局（其余玩家先进入，该玩家延迟加入）。

### 4.4 中继的代价（必须写进 UI）

中继 = 多一跳。房主→中继→客户端，RTT 约等于两者之和，且中继位置决定一切。**不要假装中继无感**：进入 relay 模式时，在记分板显示一个图标，并在延迟数字旁标注「中继」。

## 5. A4：输入冗余与服务端去重

### 5.1 冗余的账

§7.9 已定「每 tick 发 1 个，附带最近 3 个（防丢包）」。补上成本：

```
单条 cmd ≈ 12 B（tick4 + buttons2 + yaw2 + pitch2 + move2）
每 tick 发 4 条 ≈ 48 B + 头部 10 B ≈ 58 B
64Hz → 3.7 KB/s（上行，每客户端）
```

对 10 人局，服务器总入向约 37 KB/s，完全可接受。**不要为了省这点带宽去降冗余深度**——丢包时少一条 cmd，客户端就要多回滚一次。

### 5.2 去重规则（v0.3 缺失）

服务器必须维护一个「已执行 tick」窗口：

```c
struct InputWindow {
    uint32_t last_executed_tick;   // 已执行到的最大 tick
    uint16_t seen_bitmap;          // last-15 .. last 的到达位图
    uint8_t  queue_depth;          // 当前缓冲深度（目标 2 tick）
};
```

规则：

| 情况 | 处理 |
|---|---|
| `cmd.tick <= last_executed_tick` | **丢弃**（重复包，正常现象，不记日志） |
| `cmd.tick` 在 `[last+1, last+8]` 且未见过 | 入队，置位图 |
| `cmd.tick` 在窗口内且已见过 | 丢弃（冗余副本） |
| `cmd.tick > last + 8` | 丢弃 + 记警告（时钟异常或作弊） |
| 队列深度 > 4 tick | 丢弃**最旧**的，记日志（病态网络，与 §7.9 一致） |

### 5.3 迟到输入：丢弃，不快进

当某 tick 的 cmd 在服务器执行完该 tick 之后才到，**绝不能补执行**（会破坏回滚一致性，且客户端已经预测过了）。正确做法：

1. 服务器丢弃；
2. 客户端在该 tick 用的是本地预测值；
3. 下一次快照校正时自然回正。

**判据**：人为注入 5% 丢包 + 30ms 抖动，跑 60 秒，位置修正事件 < 3 次/分钟，且单次修正位移 < 0.5 m。

## 6. A5：会话恢复

### 6.1 设计

| 项 | 规定 |
|---|---|
| 票据 | 32 B：`client_id(16) + expiry(4) + HMAC-SHA256 截断(12)`，房主内存持有 |
| 有效期 | 120 秒（跨回合，不跨比赛） |
| 恢复流程 | TCP `HELLO` 带 ticket → `HELLO_ACK` 直接回 `RESUME_OK` → 补发 `FULL_STATE` |
| 恢复时**不做** | 不重跑资产清单、不重做打洞（沿用上次的候选，若 30 秒内曾连通） |
| 超过有效期 | 走冷启动流程 |
| 回合内重连 | 一律观战到下一回合（§7.7 已定，此处只补协议实现） |

**判据**：拔网线 10 秒后插回，5 秒内回到可操作状态，且比分/经济/炸弹状态与服务器一致（逐字段比对日志）。

## 7. B1：MTU 与分片（v0.3 完全缺失）

### 7.1 为什么必须有

自研 UDP 最常见的翻车点不是算法，是**大包**。§8.1 选了 `.map` 直读，意味着地图数据可能不小；§3.5 的 `configstring` 也明确是「一次性下发」。任何一个超过路径 MTU 的包，要么被静默丢弃（IPv4 且 DF=1），要么被分片后丢一片全废（且没有重传就是永久缺失）。

### 7.2 规格

| 项 | 值 | 理由 |
|---|---|---|
| 保守 MTU | **1200 B** | RFC 8085 建议；IPv6 最小链路 MTU 1280 − 40(IPv6 头) − 8(UDP) 后留余量，兼容隧道 |
| 探测 | 可选 PLPMTUD，v0.1 **不做** | 局域网固定 1500，不值得 |
| 快照分片 | 支持 | 单快照 > 1100 B 时启用 |
| 分片头 | `snap_id(16) + frag_idx(8) + frag_total(8)` | 8 位足够（255×1100 ≈ 280 KB） |
| 丢片策略 | **整包丢弃，等待下一 tick** | 快照有时效性，重组一个过期快照毫无价值 |
| 可靠流分片 | **不做** | 改用 512 B 分块 + 独立重传（A2），语义更简单 |

**反模式（明确否决）**：

| 做法 | 为什么错 |
|---|---|
| ~~为快照做重组缓冲，等齐所有分片~~ | 快照的价值随时效衰减；等 3 个 tick 重组出的旧快照，不如用当前 tick 的新快照 |
| ~~靠 IP 分片~~ | 中间设备会丢分片、NAT 会改写 ID，行为不可控 |
| ~~把 MTU 设成 1500 图省事~~ | 一旦有人走 VPN/隧道（Tailscale、WireGuard），1500 必炸，且症状是「偶发人物静止」 |

**判据**：注入 1400 B 的快照（强制分片），丢包 10%，游戏内不出现「人物卡住不动超过 200 ms」。

## 8. B2：带宽预算（v0.3 只有 CPU 预算）

### 8.1 逐项估算（5v5，10 实体）

| 流 | 单包 | 频率 | 单客户端带宽 |
|---|---|---|---|
| 快照（delta） | 60–120 B | 64 Hz | 4–8 KB/s |
| 事件 | 20 B | ~20/s | 0.4 KB/s |
| cmd（上行，含冗余） | 58 B | 64 Hz | 3.7 KB/s |
| ACK / PING | 16 B | 10 Hz | 0.2 KB/s |
| **合计（下行）** | | | **≈ 5–9 KB/s** |
| **合计（上行，每客户端）** | | | **≈ 4 KB/s** |

服务器侧（listen server，房主）：

```
下行 = 9 客户端 × 8 KB/s ≈ 72 KB/s ≈ 0.6 Mbps
上行 = 9 客户端 × 4 KB/s ≈ 36 KB/s ≈ 0.3 Mbps
```

**结论：带宽不是瓶颈，R23 风险可降级。** 真正的瓶颈是**初始 full_state**：一张 40×40 图 + 材质清单可能 1–3 MB，如果走 UDP 就是灾难。**这就是 A1 存在的意义**——它必须走 TCP + gzip + 落盘缓存。

### 8.2 快照压缩的优先级（别过早优化）

| 手段 | 收益 | 何时做 |
|---|---|---|
| 字段级 delta（baseline = 最近 ack） | 60–80% | M5 必做 |
| 位置量化（1/16 m，16 bit/轴） | 25% | M5 |
| 角度量化（yaw 用 9 bit，pitch 8 bit） | 5% | M5，顺手 |
| 实体剔除（不可见不传） | 30–50% | v0.2 |
| 位打包（bitstream） | 10% | v0.2 |
| ~~通用压缩（zstd/lz4）~~ | 5–10%，CPU 换带宽 | **v0.1 不做**，局域网不缺带宽 |

## 9. D：反向利用——把「兜底」换成「精度」

这一节是本文的核心论点：**NetherNet 值得抄的不是它藏延迟的能力，而是它把「预测 / 权威 / 回溯」三者的边界划得很干净。** 划干净之后，参数可以按自己的场景重定。

### 9.1 回溯窗口：用公式算，不用经验值

```
W ≥ RTT_max + interp_delay + jitter_buffer
  = 30 ms + 15.6 ms(1 tick 插值) + 5 ms
  ≈ 51 ms
  → 64 tick 下 4 tick，取 6 tick（93.75 ms）作安全裕度
```

对照：Source 引擎默认 `sv_maxunlag = 1.0 s`，Overwatch 约 200 ms。它们是为了兜住 200ms 玩家；你只需要兜住 30ms 玩家。**窗口每多 1 tick，就要多存一份世界状态、多一次潜在的重放开销**——没有理由给不存在的网络条件付费。

### 9.2 回溯只需要回滚「活体的 hitbox」，不需要回滚世界

这是一个能省掉大量复杂度的关键判断：

| 对象 | 是否回滚 | 理由 |
|---|---|---|
| 玩家 hitbox（位置/姿态） | **是** | 命中判定的唯一变量 |
| 静态几何（`.map` brush） | 否 | 整局不变，直接查当前 |
| 门/可动机关 | 是（需记录状态变更 tick） | 开合会遮挡子弹 |
| 可破坏物 | **v0.1 不做**；将来做则需几何版本号 | 与 §2.2「Jolt 重新评估」联动 |

**实现**：环形缓冲存 `HitboxSample[64]`（每 tick 一条，含 pos + 3 段高度倍率 + crouch 标志）。命中回溯时按 `cmd.tick` 取相邻两帧，按 `frac` 插值——**只存每 tick 的样本是不够的，必须插值**，否则 64Hz 下会出现「1.5 cm 的台阶式误差」，在 600 u/s 的滑铲上会被玩家感觉到。

### 9.3 客户端预测命中（这是局域网才敢做的事）

§7.1 A4 目前定的是「客户端只预测枪口位移/后坐力/音效/抛壳，**不预测伤害与 hitmarker**」。这条在保守意义上正确，但它放弃了你最大的架构优势：

> 你有确定性 pmove（§5.5）、有无状态计数式 RNG（§7.8）、有同一份回溯代码（§7.3）。**那么客户端完全可以用同一个函数、同一份 hitbox 历史、同一个 `(tick, shooter, shot_index)` 算出与服务器完全一致的命中结果。**

于是可以升级为：

| 层 | 客户端行为 | 服务器行为 |
|---|---|---|
| 命中判定 | 本地算，立即弹 hitmarker + 命中音 | 用同函数复算，作为权威 |
| 不一致时 | 收到 `HIT_REJECT` 事件，撤销 hitmarker（视觉淡出，不回滚血条数字） | 记录不一致日志 |
| 伤害数字 | **仍等服务器**（避免血条抖动） | 权威 |

**前提条件（三个，缺一不可）**：
1. 客户端必须保存与服务器等长的 hitbox 历史（`> W`，建议 1 秒 = 64 帧）——这是 v0.3 没写的**新增要求**；
2. `shot_index` 必须在 cmd 里带上，且服务端回执按 `(tick, shot_index)` 对齐（§7.1 A4 已有）；
3. 双方使用同一编译单元、同一浮点设置（否则 §10.3 的容差会吃掉判定）。

**风险与回退**：给一个 `cl_predict_hit 0/1` 开关，默认 1；若不一致率 > 0.5%，关掉回退到「等服务器」。M6 做 A/B 对比。

### 9.4 128 tick：条件化尝试，而不是现在就定

§7.2 定 64Hz，理由是 5v5 + 局域网。但同样的逻辑（商业妥协 vs 自身条件）也适用于 128Hz：

| 项 | 64 tick | 128 tick |
|---|---|---|
| 单 tick 预算 | 15.625 ms | 7.8125 ms |
| §7.9 的 sim 预算（4 ms） | 占 26% | 占 51% |
| 快照带宽 | 8 KB/s | 16 KB/s |
| 1 秒回滚重放量 | 64 tick | 128 tick |

**判据（M5 稳定后测，不提前决定）**：
- sim p99 < 3.5 ms（即 128 tick 预算的 45%）；
- 重放 128 tick 的耗时 < 1.5 ms；
- 两者都满足才升 128，否则保持 64 并把「64 是我们的选择」写进设计说明——**别让 64 看起来像妥协**。

## 10. 明确不抄的三件（含定量理由）

### 10.1 anycast 接入

不是「用不上」，是**有害**。

| 问题 | 机制 | 对本项目的后果 |
|---|---|---|
| 会话路径漂移 | BGP 收敛（通常 30–90 s）期间，同一五元组的后续包可能落到另一个 PoP | 一次漂移 = RTT 阶跃 50–150 ms → 一次大幅回滚 → 严格判定下等于「凭空 miss」 |
| 非对称路径 | 去程与回程走不同 PoP | 抖动上升，§7.9 的 2 tick 输入队列频繁溢出 |
| 无法定位 | 玩家报「卡」，你 ping 同一个域名却正常 | 排查成本极高 |

**结论**：`~~用 anycast 做游戏接入~~`，理由写「与严格命中判定不兼容」。这条要进 §2.2 否决表。

### 10.2 WebRTC 全套栈（DTLS/SCTP/GCC）

与你否决 GNS 是同一个理由，只是换了层皮：SCTP 的重传与拥塞语义假设「数据要送达」，而快照的语义是「丢了就丢了，下一个更重要」。引入它等于给自己造一个 3000 行的黑盒，且排查问题时无法用 `tcpdump` 直接读懂。

**只借**：候选交换、优先级、连通性检查、失败降级。**不借**：握手、加密、拥塞控制、多流。

### 10.3 微软的中继与骨干

你自己就是服务器。v0.2 真有跨城需求时，买一条 UDP 中转（按流量计费）+ 自己做 A3 的选路即可。**别自建骨干**——那是另一个项目。

## 11. 与 v0.3 的冲突裁决

写文档最有价值的时刻，是发现旧文档自己和自己打架。本轮发现三处：

| # | 冲突 | 原文 | 裁决建议 |
|---|---|---|---|
| C1 | 延迟补偿做不做 | §7.1 表格写「⏸ 局域网阶段先不做」；§7.3 标题写「v0.2 改为：必须做」 | **统一为「v0.1 不做，M6 必做」**。§7.1 表格改为「⏸ v0.1 不做（M6 起必做）」 |
| C2 | 延迟补偿的排期 | §12.1 v0.1 定义写「❌ 延迟补偿」；§7.3 要求「第一天建 hitbox 历史环形缓冲」 | 不矛盾但表述割裂：**缓冲在 M6 建（约 50 行），补偿逻辑 M6 做**；v0.1 只是不启用。§7.3 的「第一天」改为「M6 第一天」 |
| C3 | 输入队列深度 vs 冗余深度 | §7.9 队列 2 tick；A4 每 tick 发 3 个历史包 | 两者不冲突，但**必须补去重**（本文 §5.2），否则冗余包会被当成新输入入队，队列瞬间溢出 |

另有一处**范围现实性**提示（非冲突）：

> §1.3 写「网络：局域网 / 同城（ping < 30ms）」，但 §1.3 同时写「自己 + 3–9 个朋友」。这两条在现实中会漂移——朋友会回老家、会换运营商。A3 的工期（3–5 天）应视为**保险**，而不是可选优化。
