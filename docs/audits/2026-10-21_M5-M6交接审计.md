# 1. P0 · 协议位域扩容（新发现）

## 1.1 证据

```cpp
// sim/net/snapshot.cpp:9-16
kFieldPos     = 1u << 0,
kFieldVel     = 1u << 1,
kFieldStatus  = 1u << 2,   // flags, impulses, state
kFieldTimers  = 1u << 3,   // state_ticks, dash_cooldown
kFieldYaw     = 1u << 4,   // view yaw
kFieldExtra   = 1u << 5,   // wall_normal, vault_dir, vault_rise (R9)
kFieldCharge  = 1u << 6,   // recharge, speed_coefficient
kFieldAll     = 0x7F,
```

```cpp
// sim/net/snapshot.h:17-21
// bit0 on_ground, bit1 crouched, bit2 active, bit3 jump_was_down,
// bit4 slide_was_down, bit5 dash_was_down, bit6 vault_was_down.
uint8_t flags = 0;
```

**两处都只剩 1 个 bit。**

## 1.2 M6 需要多少新位

| 新增数据 | 需要 | 说明 |
|---|---|---|
| `hp` / `armor` | **1 个 group** | 当前快照完全没有生命值（GAPS §4 已记） |
| `weapon_id` / `ammo` | **1 个 group** | 满编对局必须知道对方拿什么 |
| `fire_cooldown` / `reload_ticks` | 1 个 group，或并进 `kFieldTimers` | 并进去可以省一位 |
| `firing` / `reloading` / `ads` 状态 | **3 个 bit** | flags 只剩 1 位 |
| `alive` | 1 个 bit | 死亡/重生需要 |

**结论**：**mask 至少需要 +2 位，flags 至少需要 +4 位。现在都不够。**

## 1.3 具体方案

### mask：`uint8` → `uint16`

| bit | 字段组 | 状态 |
|---|---|---|
| 0 | `kFieldPos` | 已有 |
| 1 | `kFieldVel` | 已有 |
| 2 | `kFieldStatus` | 已有 |
| 3 | `kFieldTimers` | 已有 |
| 4 | `kFieldYaw` | 已有 |
| 5 | `kFieldExtra` | 已有 |
| 6 | `kFieldCharge` | 已有 |
| **7** | **`kFieldVitals`** | **M6：hp / armor** |
| **8** | **`kFieldWeapon`** | **M6：weapon_id / ammo / cooldown** |
| 9 | `kFieldTeam` | 预留（队伍、选边） |
| 10–15 | — | 预留 |

```cpp
constexpr uint16_t kFieldAll = 0x01FF;  // bit0..bit8
```

### flags：`uint8` → `uint16`

| bit | 含义 | 状态 |
|---|---|---|
| 0 | `on_ground` | 已有 |
| 1 | `crouched` | 已有 |
| 2 | `active` | 已有 |
| 3 | `jump_was_down` | 已有 |
| 4 | `slide_was_down` | 已有 |
| 5 | `dash_was_down` | 已有 |
| 6 | `vault_was_down` | 已有 |
| **7** | **`firing_was_down`** | **M6** |
| **8** | **`reloading_was_down`** | **M6** |
| **9** | **`ads_was_down`** | **M6** |
| **10** | **`alive`** | **M6** |
| 11–15 | — | 预留 |

> **低 7 位保持不变**，新增从 bit7 开始，语义完全向后清晰。

### 协议版本

```cpp
// sim/core/version.h
#define BP_PROTOCOL_VERSION 6
```

| 文件 | 改什么 | 判据 |
|---|---|---|
| `sim/net/snapshot.h` | `uint8_t mask/flags` → `uint16_t`；新增位定义 | 编译通过，字段注释与 `kFieldAll` 一致 |

### 防止再次犯：加静态断言

```cpp
// snapshot.cpp
constexpr uint16_t kFieldUsed = kFieldPos | kFieldVel | kFieldStatus | kFieldTimers
                              | kFieldYaw | kFieldExtra | kFieldCharge
                              | kFieldVitals | kFieldWeapon;
static_assert((kFieldUsed & ~kFieldAll) == 0, "kFieldAll 未覆盖全部字段组");
static_assert(kFieldAll != 0xFFFF, "位域已满，必须扩到 uint32");
```

第二条断言的价值：**下次位域再满时，编译期就会报错**，而不是等到运行中发现“某个字段不同步”。

## 1.5 风险

| 风险 | 缓解 |
|---|---|
| 每玩家多 1 字节 mask | 20 玩家 × 64 tick = 1.28 KB/s，可忽略 |
| 旧 demo 无法播放 | demo 头写入版本，明确拒绝并提示；发版前留带符号二进制 |
| 快照变大触发 IP 分片 | **这正是 AUD-23 必须在 M6 前解决的原因**（见 2.1） |
| 闸门基线全部要重跑 | 一次性成本，换掉 M6 中途改协议 |

## 1.6 为什么现在最便宜

| 时点 | 代价 |
|---|---|
| **现在**（7 个 group） | 半天；只动协议层，射击代码尚未写 |
| M6 中途 | 射击代码已基于旧快照写；demo 格式、闸门基线、桥接口全要跟改 |
| M7 之后 | 还要连带动画状态字段，二次扩容 |

> **DEBT-01（acked_cmd 残骸）和 DEBT-16（包头 9B vs 10B）都写着“要么协议 v6”**——正好这次一起清掉，一次版本升级解决三条。

# 2. M5 遗留阻塞项

## 2.1 AUD-23 · 分片只在闸门里，真实链路没套（P1，M6 前必办）

**现状**：`FragmentedTransport` 只在测试里组装，`bridge/net_gateway.cpp` 的真实 UDP 没套。

**为什么阻塞 M6**：现在快照小（每玩家约 40 字节），满编 10 人约 400 字节，不到 MTU。**加上 hp/armor/weapon 后，加上包头，很容易逼近或超过 1200 字节的安全线**，一旦超了就走 IP 分片——而 IP 分片丢一片整包报废，表现为“偶尔整帧丢失、人物瞬移”。

**修法**：把 `FragmentedTransport` 接到真实链路，`add_client` 时按 MTU 分片。

**判据**（沿用你们自己的）：
> 真实链路包 >1100 B 时 `[frag] sent/reassembled` 计数增长且快照完整；10 人场景跑通。

**建议顺序**：**先做协议 v6，再做 AUD-23**——因为 v6 之后包刚好变大，正好用它验证分片。

## 2.2 AUD-20 · 客户端落后不补 tick（P1）

**现状**：一次 >110 ms 卡顿吃掉 lead+slack 后，命令永久 Late，只能重连。

**根因位置**：`godot/main.gd:502-511`

```gdscript
accumulator += delta
var ticks := 0
while accumulator >= TICK and ticks < 5:
    sim.step()
    accumulator -= TICK
    ticks += 1
if ticks == 5:
    accumulator = 0.0      # ← 这里
```

卡顿超过 5 tick 时，累积时间被**直接清零**，时间线永久偏移。之后客户端认为的 tick 与服务器对不上，命令全部被判 Late。

**修法**（两个方向，建议都做）：

1. **保留余量而不是清零**：`accumulator = fmod(accumulator, TICK)`，并记录丢弃的 tick 数
2. **服务器侧补 tick**：当窗口内连续 Late 超过 N 次，客户端主动追 1–2 tick（`ServerClock::advance()` 跳一次）

**判据**：
> 客户端停 300 tick 再恢复，late 停止增长且位置继续前进；无需重连。

**注意**：这个问题和 §3.1 的渲染插值**在同一段代码里**，一起改。

## 2.3 AUD-26 · UDP 不校验源地址（P1）

**现状**：`udp_transport.cpp:26-30` 丢弃源地址，客户端不校验包来自 `connect_peer` 的主机。

**后果**：同网段任何人可注入快照或命令。**两个人局域网对局就能被踩**（哪怕只是误配）。

**修法**：源地址不符即丢并计数。

**判据**：
> 闸门用第二个 socket 注入应被拒；合法包计数正常增长。

## 2.4 AUD-27 · 正常离开不释放槽位（P1）

**现状**：`MatchHost` 槽位只在 `MATCH_START` 前的中断路径释放；正常离开后 bridge 从不 `release`。

**后果**：2 槽房，两个人各进一次后**房间永久 RoomFull**。

**修法**：`NetServer::remove_client` → `MatchHost::release(slot)` 回调。

**判据**：
> 2 槽房连续 join/leave 3 次仍能进。

# 3. 顺手修的两项

## 3.1 本地渲染插值缺失（P2，但影响观感）

**现状**：`godot/main.gd:524-528`

```gdscript
var position: Vector3 = sim.get_position()          # 每 tick 才变（64 Hz）
camera.position = position + Vector3(0.0, sim.get_eye_height(), 0.0)
camera.rotation = Vector3(pitch, godot_yaw, 0.0)    # 每帧更新（144 Hz+）
```

**算一下**：

| | 周期 |
|---|---|
| 模拟 tick | 15.625 ms |
| 144 Hz 渲染 | 6.94 ms |

**同一个位置渲染 2–3 帧再跳一次** → judder。

更糟的是**视角每帧平滑、位移阶梯状**：转头时画面连续动、身体在跳格，比纯掉帧更扎眼。

**为什么 Godot 的 physics interpolation 帮不上**：那个插值器只认识它自己物理服务器驱动的节点；我们的 transform 是 GDExtension 从外部每 tick 写入的，引擎没有“上一帧”可插。

**修法**（约 5 行）：

```cpp
// bridge：多暴露一个上一 tick 的位置
Vector3 get_prev_position() const;
float   get_prev_eye_height() const;
```

```gdscript
var alpha := accumulator / TICK
var p: Vector3 = sim.get_prev_position().lerp(sim.get_position(), alpha)
var eye: float = lerp(sim.get_prev_eye_height(), sim.get_eye_height(), alpha)
camera.position = p + Vector3(0.0, eye, 0.0)
```

> `eye_height` 也要插值——蹲下时它会变，不插值会看到相机瞬间下沉。

**远端玩家**已经用了插值（`bridge/sim_bridge.cpp:157` 的 `remote_sample`），**缺的只有本地这一条**。

**判据**：
> 144 Hz 显示器上慢速横移，录 240 fps 慢动作，相邻帧位移差值的方差下降一个数量级。

## 3.2 E 键与拆包交互冲突（P2）

**现状**：键位是 **C 翻越 / Q 墙跑 / E 爬墙 / X 冲刺**（瓦洛兰特风格布局）。

**冲突**：爆破模式需要**交互键**（下包、拆包、开门）。CS 与瓦洛兰特都用 `E` 做交互，而 `E` 被爬墙占了。

**为什么现在改**：
- 改键位只改 `sim/data/keybinds.toml` 一个文件
- 但一旦 M3 的 parkour 闸门基线是按现有键位录的，改键后要重录
- 越往后（动画、教程、肌肉记忆）越贵

**建议**：
```
爬墙：E → Shift（或鼠标侧键）
交互：留给 E（M6/M8 拆包时用）
```

**判据**：
> `--test-parkour` 全绿；键位配置文件里 `Interact` 与 `WallClimb` 不共用同一键。

# 5. M6 的三个设计决策

## 5.1 WeaponDef 放哪

**建议**：新建 `sim/data/weapons.toml`，**不要塞进 `movement.toml`**。

理由：`movement.toml` 已经参与 `params_hash`，而这个哈希用于跨机一致性校验。武器表在调参期会高频改动，混在一起会让每次调枪都触发“参数哈希变了”的告警，噪音掩盖真问题。

**接口建议**：

```toml
[weapon.rifle]
damage_near = 32
damage_far  = 22
falloff_start = 15.0
falloff_end   = 40.0
rpm = 600
draw_time = 0.45
put_away_time = 0.35
sprint_time = 0.25
aim_time = 0.22
speed_coefficient = 0.92
headshot_mult = 5.0
```

## 5.2 什么进快照、什么进 rollback

| 数据 | 进快照 | 进 rollback 历史 | 理由 |
|---|---|---|---|
| hp / armor | ✅ | ❌ | 客户端不预测伤害（A4 已定），只需显示 |
| 弹药 / 开火冷却 | ✅ | ✅ | 客户端要预测“按了能不能开火” |
| 后坐力 index | ❌ | ❌ | 客户端算；服务器下发 `punch` 做增量校正（A4） |
| 当前武器 | ✅ | ✅ | 切枪改变移速（`speed_coefficient`） |
| `alive` | ✅ | ✅ | 死亡后输入应被忽略，预测要知道 |

> **后坐力 index 不进快照**是 A4 的直接推论。否则每开一枪同步一个 uint8，收益为零、包体白涨。

## 5.3 腿倍率是否硬编码

`hitbox.h` 有 `zone_multiplier(HitZone, const MovementParams&)`，头倍率从 `movement.toml [damage] headshot_mult = 5.0` 读。

**要确认**：腿倍率 `0.7` 是常量还是可配。

**如果是常量**，挪进 toml——这与 AUD-28（“手感常量仍是字面量”）是同一类问题，而且铁律 I 要求“任何影响手感的数值必须可热重载”。

# 附录 A · 协议 v6 字段组详细设计

## A.1 快照结构（v6）

```
Snapshot {
  u32 tick
  u32 acked_cmd            // ← DEBT-01：要么真填，要么删
  u32 baseline_tick        // 0 = full
  u8  player_count
  for each player:
    u8   player_id
    u16  mask               // ← uint8 → uint16
    if mask & Pos:     vec3 pos
    if mask & Vel:     vec3 vel
    if mask & Status:  u16 flags; u8 impulses; u8 state
    if mask & Timers:  u16 state_ticks; u16 dash_cooldown; u16 slow_ticks
    if mask & Yaw:     f32 yaw
    if mask & Extra:   vec3 wall_normal; vec3 vault_dir; f32 vault_rise
    if mask & Charge:  u8 recharge; f32 speed_coefficient
    if mask & Vitals:  u16 hp; u16 armor          // M6 新增
    if mask & Weapon:  u8 weapon_id; u16 ammo; u16 cooldown  // M6 新增
}
```

**每玩家新增上限**：`2（mask）+ 4（vitals）+ 5（weapon）= 11 字节`
**10 人满编新增**：约 110 字节。仍在 MTU 安全线内，但**必须先把 AUD-23 的分片接上**作为保险。

## A.2 demo 格式

demo 头已含 `build_id`（AUD-30 提到初始状态不完整）。v6 追加：

```
u16 protocol_version
```

读取时：

| 情况 | 行为 |
|---|---|
| 版本一致 | 正常回放 |
| 版本不一致 | **明确拒绝**并打印 `demo protocol vN != engine vM`，退出码 2 |
| 版本字段缺失（旧 demo） | 视为 v5，警告后尽力播放 |

> 判据纪律：**“尽力播放”必须打印警告，不能静默**——否则又会变成“能打印不能失败”那一类。

## A.3 闸门要改的地方
